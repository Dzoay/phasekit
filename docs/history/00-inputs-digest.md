## CoolProp map implications (docs/coolprop-map/NN-*.md)

### 01-api-state
- Make flash a pure function: fn flash(&Model, Input, &FlashOptions) -> Result<State>. CoolProp's mutable instance is poisoned by its own flash routines (sticky iphase_twophase after QS/HQ) and by failed updates, so no solver may mutate shared or persistent state.
- Phase hints must be per-call values, never stored on a model or state; the result Phase enum must exclude Unknown/NotImposed.
- Backend capability must be declared, not discovered by exception: PCSAFT really supports 4 pairs, INCOMP 4 + QT(Q=0), HEOS 39 of 43. Encode supported physical pairs per model and test the full 19 x basis matrix.
- A single Input enum over 19 physical pairs, with the basis carried by the quantity type and one to_molar(M) normaliser, removes R2/R3/R4 (name collisions, unreachable QS/HQ pairs, HmassT/TUmass asymmetry) by construction.
- Never use Rust enum discriminants as an ABI: CoolProp renumbered 64/86 parameters and 34/36 input pairs between v7.2 and v8 and is doing it again on master; use string names or pinned append-only #[repr] values in a separate C-ABI crate.
- The kernel takes typed immutable options and never reads env or global config; CoolProp's own library code toggles global config mid-computation (TabularBackends.cpp:129,197), so any global is unsafe under concurrency.
- The model must be immutable and Arc-shared: per-instance deep copies (~111 KiB for Water) and evaluation caches inside EOS objects are what block thread sharing; the derivative bundle should live in the State.
- The generic first/second partial-derivative engine (Jacobian ratio over (T, rho)) is backend-agnostic and branch-free: port it early, extend second derivatives to G, Cp, Cv, w, and test with FD plus identities (CoolProp's own FD test skips 5 of 19 variables).
- One strict FluidSpec parser shared by every entry point, with options as a typed struct; CoolProp's string grammar silently accepts MEG-abc% as 0% and breaks JSON options on '&' and '['.
- Oracle hygiene for TDD: fresh instance per fixture case (instance poisoning), empty COOLPROP_*/PXFLASH_* env, reset reference states, and never encode R3/R4/R5/R6/R7/R12/R13/R17/R26 behaviour as expected values.
- Open questions: Should the compat PropsSI layer reproduce any CoolProp defect (echo shortcut, Q=-1 sentinel, unreachable QS/HQ pairs) for parity, or document deviations? (doc proposes: none) | Is mixture composition part of the Model (Arc per composition) or of the Input/State? | Eager vs OnceCell derivative bundle in State: needs a benchmark against flash cost | Do the sticky-twophase sites in FlashRoutines (8 specify_phase calls) also affect mixtures and update_with_guesses paths? Relevant when choosing oracle fixture isolation | Which C-ABI consumers (Excel, LabVIEW, Modelica, Fortran) are required, and therefore when the C-ABI crate is needed | Phase-classification contract for cubic/PC-SAFT backends (R26): kernel-defined or per model? | Model cache policy for the compat API under WASM memory limits (bounded LRU vs explicit clear)

### 02-helmholtz-eos
- Type three distinct notions: Reducing (EOS parameter, sole source of tau/delta), EosCriticalPoint (computed lazily or from superancillary), PublishedCritical (metadata). CoolProp conflating them causes mu != g and mixture alpha0 errors for 15+ fluids
- Compile each fluid into an immutable Arc<PureEos> (Send+Sync) with derivatives as per-state values; CoolProp's deep copies (6 live per state, no move ctor, 56-96 KB SA strings kept) cost ~48 us per construction vs ~3.7 us for an update+h+cp
- One separable 'exp-of-jets' kernel (B-factor recurrence, one exp per term) covers Power/Exponential/Gaussian/Lemmon2005/DoubleExponential/GaoB = 99.8% of default terms; NonAnalytic (5 terms, Water/CO2) stays scalar with explicit singular behaviour at delta=1
- Compute alpha0 as one tau-jet per state (or per isotherm); CoolProp does a full alpha0 container pass for each distinct derivative and always computes an unusable 4th order
- Output scaled derivatives tau^i delta^j d^(i+j)alpha with a Want mask; provide exact delta->0 Taylor coefficients for virials instead of evaluating at delta=1e-12 (C wrong at 1e-5 for 45 fluids)
- Loader must encode JSON semantic quirks explicitly: '0 means absent' for l/m exponents, GaoB eta stored negated, PlanckEinstein theta sign flip, integral-float d/l (277/161 values stored as 1.0), cp0 block Tc must equal T_r (R123/R11[1] violate), Ttriple key ignored
- Lazy per-fluid load (OnceLock) with the superancillary in a second lazy cell; eager superancillary construction costs ~1.8 s and ~11 MB at import in CoolProp
- TDD oracle tolerance ~1e-14 relative on alpha (independent evaluator matched to 5.8e-14) and ~1e-12 on derivatives; a divergence registry is needed for known oracle bugs (mu, mixture alpha0, C virial, two-phase cp/cv, R123 cp0, H2 melting, Simon bound, RESET)
- Property API returns Result and keeps two-phase rules in a separate layer; CoolProp silently returns meaningless two-phase cp/cv
- No globals in kernels: drop deriv_counter, config reads (ENABLE_SUPERANCILLARIES changes T_critical()), and the name-keyed MeltingCaloric cache; reference states as immutable with_reference() values
- Open questions: Divergence policy: match the 8.0.0 oracle behind a compat flag or follow literature by default for mu, mixture alpha0, C virial, two-phase cp/cv, R123 cp0, H2 melting, Simon bound? | Data snapshot: v8.0.0 JSON for oracle parity vs origin/master (corrected reducing densities 2acbbc82, refit superancillaries 66859efb, R-1132a)? | Which critical point is public: JSON STATES.critical, reducing state, or EOS numerical critical point (25 fluids differ, up to 2.3 K)? | Expose the 23 alternate EOSs? If yes, association term moves from defer to P1 | Reference-state semantics: immutable per-model only, or a process default mirroring set_reference_state; reproduce published not-exactly-IIR offsets? | Behaviour at non-analytic singularities (delta=1 4th derivative infinite, cp divergent at reducing point): +-inf, NaN+error, or CoolProp's 10eps nudge? | What is the correct H2/o-H2 melting curve below the Datchi validity range (needs literature check)? | Is max derivative order 4 sufficient, or should jet order be generic? | Vector exp/ln choice and accuracy budget for SIMD kernels vs scalar reference

### 03-flash-solvers
- The flash must be a pure function `flash(&Model, Spec, &FlashOptions) -> Result<State, FlashError>` with any phase hint passed per call. CoolProp's mutable specify_phase flag leaks across calls (DQ/HQ/QS never clear it) and is silently wiped by PH/DH/HS. This is verified in the oracle and still present on master.
- Domain checks belong in the model, independent of config. Below Ttriple, CoolProp fabricates two-phase DT states whether SA is on (extrapolated Chebyshev) or off (p = 1.1e-4 Pa). The Rust SA eval should return Result and extrapolation should be opt-in.
- Non-unique input pairs need first-class handling: an `Ambiguous`/`MultipleSolutions` error carrying the roots as data, plus a RootPolicy. T+H in compressed liquid, T+S/T+U for cold water, and Q-pairs with 2-3 roots (Water h'', R1234ze(E) s'') are all real. For T+X, CoolProp parity means silently wrong two-phase answers, so the literature/EOS must arbitrate there, not the oracle.
- Root solvers should return `Root{x, f, iters, status}` evaluated at the returned x, check residual and step together, and report exhaustion as an error. CoolProp returns x_{n+1} with the state at x_n, never checks TOMS748 max_iter, and NDNewton loops with x = HUGE. Tolerances should be typed relative, absolute or log-axis; absolute 1e-9 mol/m³ gave a 6.1% ST error.
- The SA data is well suited to an immutable, SoA, SIMD-friendly layout. All 130 fluids are degree 12 with identical piece boundaries for rho', rho'' and p, dyadic to depth 24 (Chlorine excepted), and 318k coefficients total ~2.5 MB as f64. One piece lookup can feed 3 (or 9 with calorics) Clenshaw chains, and a dyadic index allows branch-free lookup.
- Precompute offline (or once per fluid under OnceLock) what CoolProp builds at load or first use under a mutex: monotonic extrema, the T(ln p) inverse and the h/s/u caloric curves. That removes ~2 s of eager import, the 2 ms and 45-115 ms first-use spikes, and the per-call mutex on every PQ/PH/PS.
- Expose both critical points explicitly: published, and numerical (SA Tc_num, which may differ, e.g. Chlorine's last piece ends 1e-4 K early). CoolProp switches T_critical() by a global config, and QT at the published Water Tc throws.
- Use a scalar reference kernel with no FMA, in CoolProp's Clenshaw order, for bit-level oracle parity. SIMD variants are tested against the scalar Rust reference with ULP bounds. Branchy flashes (HS cascade, P+X nested solve, D+X interval method) stay scalar and are batched per request.
- Port only reachable behavior: drop dead code (HSU_P Newton, HS_flash_singlephase, ODE/Romberg, solve_for_Tq_DX), env kill-switches, Q sentinels (-1/±1000/1e9/10000), the legacy 2%/5% ancillary bands for SA fluids, and exception-driven try/catch cascades. Replace them with ordered Result strategies and a single verify() gate.
- Open questions: Should the Rust library reproduce CoolProp's SA-extrapolated or ancillary behavior below Ttriple (supercooled liquid) behind an explicit allow_extrapolation flag, or reject it outright? | For T+H/T+S/T+U in compressed liquid, the oracle is wrong by construction. Which reference (EOS root enumeration on both branches, or literature tables) becomes the TDD oracle there? | Why does the wheel show no per-state memory cost for the retained SA JSON string? This matters only for interpreting CoolProp memory baselines, not for the Rust design. | Which post-v8.0.0 master fixes (e33bf27a log-rho, 3f06ccf7 PT state and derivatives, 42bc0667 format, 0f978943/aa7c6079 Q validation, b17661f6 mixture roots, 66859efb SA refit) are adopted as the spec where they deviate from the 8.0.0 oracle? | Should Q-pairs support fractional Q symmetrically via SA (DQ/HQ/QS) and bracket to Tc_num, rather than CoolProp's Tc-0.1 bracket and HQ's Q=1-only restriction? | Is PT exactly at psat an AtSaturation error, or a 'saturated, ambiguous' result, given that CoolProp's behavior depends on whether T is below 0.9 Ttriple + 0.1 Tmax_sat?

### 04-vle-mixtures
- The mixture ideal part must evaluate each component's alpha0 in that component's own reducing variables, and an invariant test 'z=(1,0) equals the pure fluid up to the R policy' is needed. CoolProp 8.0.0 and master both violate this for 15 fluids (crit != reduce), so oracle comparisons of h, s, cp and mu for those fluids need a known-deviation fixture.
- Zero mole fractions must be trimmed when the model instance is built, not guarded. Second-order x-derivatives of the GERG reducing function have no limit at the both-zero corner (c7d6a1aa), so any envelope, critical or Newton-VLE code on an untrimmed composition is ill-defined.
- The departure-function table should be one sparse upper-triangular list of (i, j, F, &'static terms) for F != 0, evaluated once per unordered pair and indexed symmetrically. CoolProp evaluates both orientations because its composition derivatives read [i][k] for every k.
- Composition derivatives must come from one mole-number AD path. CoolProp's hand-coded 181 functions carry a convention flag whose XN_DEPENDENT branches are partly unimplemented or throw, and an ideal-term bug in the last row that corrupted Hessians until 014c8186.
- Envelopes and critical-point searches must be immutable values passed explicitly as optional hints. In CoolProp, a cached PhaseEnvelope changes which PT/PQ/QT algorithm runs and even overrode imposed phases (aeea05e4).
- Mixture BIP data needs explicit provenance and a model-family selector. HEOS 8.0.0 uses Gernert/EOS-CG for all 15 air/water/CO2/CO/Ar pairs (including the dry-air N2-O2-Ar pairs) rather than GERG-2008 or Lemmon-2000, and master now keeps multiple records per pair with the last in force.
- Single-phase root selection must enumerate all density roots and test material stability. CoolProp's two-stationary-point assumption and its SRK pre-screen produced a silent wrong 'gas' root (#1).
- The second-order PT split should optimise minority-phase mole numbers with an unscaled Gibbs gradient, and GDEM should be try-then-revert. 014c8186 shows that the beta(1-beta)-scaled gradient vanishes at the dew boundary and that the 0.95 GDEM clamp collapses near-dew splits.
- The pure-fluid path should not pay the mixture object graph: there are about 6 live CoolPropFluid deep copies per pure state, about 100 runtime pure-vs-mixture branch sites, and all 15 alphar derivatives are evaluated per update. Use distinct Pure and Mixture models behind one trait, with Arc-shared immutable component data.
- Process-global mutable configuration and libraries must become typed per-model or per-call options. In 8.0.0 the global config changes the stability algorithm, R normalisation and T_critical(), and global BIP mutators can poison the library process-wide (#5, #6).
- Open questions: Which C1/nC10 composition did the original mapper use for the 6837 MPa envelope runaway? It does not affect the rot conclusion. | Should the Rust model support only trimmed compositions, or also expose infinite-dilution limits? First-order limits exist; second-order ones do not. | For dry air via HEOS N2/O2/Ar, should the default reproduce 8.0.0's Gernert-2013 parameters (oracle parity), or GERG-2008 / Lemmon-2000? This sharpens §10 Q3. | Should mixture fugacity_coefficient() in the two-phase region keep CoolProp's throw-always semantics, or return per-phase values via a typed API? | Is the superancillary pressure expansion inaccurate at extreme low reduced pressure (MD4M, §10 Q4)? This was not re-verified here.

### 06-eos-families
- Make every residual model expose reducing-invariant derivatives (A_nm = tau^n delta^m d^(n+m) alpha). That way ideal-gas and residual parts with different reducing states can never be mixed. This is the root cause of C1 (wrong s at 8.0.0) and C2.
- The gas constant must be explicit, per-model data. CoolProp mixes 8.3144598, CODATA-2018 (identical to kB*NA) and 8.314472, plus a global NORMALIZE_GAS_CONSTANTS switch. That produces ~1.1e-6 discrepancies across 98/116 PR-vs-HEOS fluids that look like valid answers.
- Pure-cubic saturation should be superancillary plus an optional Newton polish (accurate to ~1e-13). 8.0.0's QT path is a secant with ftol 1e-5 (~1e-6 error for SRK). TDD must therefore use the superancillary, not the QT flash, as the reference.
- Cubic ideal-gas and critical constants should come from the canonical fluid DB, not a generated snapshot. The 8.0.0 cubic JSON has stale Tc and alpha0 for 11/116 fluids (D5 cp0 16% off).
- A pure cubic's critical density must come from the model (Zc = 1/3 SRK, 0.30740 PR), not the Kazakov fit. 8.0.0 reports +9.8% (PR) / +19% (SRK).
- PC-SAFT needs an ideal-gas part, phase determination based on a stability test, a lever rule in molar volume, and pure functions of T for sigma_water(T) and dielectric(T). 8.0.0 lacks h/s/cp/w, throws on supercritical PT, mis-computes two-phase Q, and evaluates the dielectric at the wrong T.
- Iterative inner solves (association X_A, density roots, VLE) must return typed convergence results. CoolProp silently accepts 100 unconverged XA iterations, grid-best density points, and VLE residuals up to 1e-3 (PQ) or 0.1 (QT).
- Write each model formula once over a numeric trait (f64, lanes, duals). CoolProp hand-codes the PC-SAFT model four times (~1.45k lines with drifted tolerances) and the cubic composition derivatives by hand (VTPR's are wrong).
- GERG is data on the shared multi-fluid model with an immutable parameter set. Its golden vectors (1,174 teqp points; CoolProp targets 1e-12 for alpha, 1e-10 for p/cv/w) are the oracle, because GERG is absent from 8.0.0.
- Oracle policy for cubics at 8.0.0: alphar, p, h, u, g, a, cp, cv, w and fugacity are usable for c = 0. Entropy, volume translation, rhomolar_critical, transport and surface tension are not.
- Open questions: Should CoolProp master (with 9b96b64b and 1ace9311) be accepted as a secondary oracle for cubic entropy and volume translation, or only analytic consistency plus teqp? | Should PC-SAFT parameters be ported from CoolProp's 180-fluid JSON, given the uncited water sigma(T) correlation and the Angstrom^3 label on the dimensionless kappaAB? | Does the Mathias-Copeman alpha apply the full polynomial above Tc in the 1983 paper? CoolProp applies it at all T. | Is ePC-SAFT (electrolytes) in scope at all? Its 8.0.0 oracle is unreliable (P3), and the tests pass at 23% tolerance. | What tolerance should TDD use for pure-cubic saturation against 8.0.0 (~1e-6 via QT) versus the superancillary (~1e-13)?

### 07-special-purpose
- Gibbs-explicit models (IF97 R1/2/5, ice Ih, Bollengier) share one property map (IF97.h:235-261, Ice.cpp:118-143, master BollengierBackend.h:322-332). A GibbsPotential trait returning one derivative bundle removes three copies and fixes R8/R10-style divergence.
- Input-pair handling must be an exhaustive, typed normalisation layer. R1 (molar HS fall-through), H1 (density passed as pressure) and I4 (fit axis = pressure) are all positional-argument bugs that typed quantities and typed fit axes rule out.
- Phase classification must be a pure function with an explicit supercritical branch and no uninitialised state. R2 and R3 come from set_phase reading a never-initialised imposed_phase_index and calling Tsat97 above p_crit.
- Batch APIs must be free functions over immutable models, never methods that mutate a state object. R5: IF97 fast_evaluate clears the caller's state despite its own contract.
- Compat-vs-exact differences must be explicit strategy enums, not hidden defaults. Candidates: IF97 Region-3 density (backward vs iterated, a documented library trade-off), HP refinement, humid-air vapour transport state, the G8-10 C_aww constants, ice g00 2006 vs 2009, the INCOMP caloric path. The TDD harness needs a register of known oracle divergences.
- Model data must pass a build-time gate: no placeholder, all-zero, non-finite or in-range-pole fits, and no Example fixtures. v8 ships I2/I3 garbage that master later scrubbed, so the oracle is wrong for those entries.
- One solver abstraction returning Result<Converged> must replace the hand-rolled 100-iteration secants (H5, H14) and Brent with maxiter = 10 (I1). INCOMP inverses should use safeguarded Newton with analytic dh/dT = c, which also fixes the endpoint bracket failures.
- Humid air must take its water, air and ice models by injection and use one phase-boundary predicate. At v8 one call mixes IF97 psat, IAPWS-95 saturation and IAPWS-95-at-IF97-density (H3), with inconsistent > / >= thresholds at 273.16 K.
- REFPROP stays out of core: a process-global, non-thread-safe proprietary FFI that is useful only as an optional second oracle for HEOS-side fluids, in a separate process.
- Open questions: IF97 default: IAPWS-exact (Region-3 Newton, HP refinement, low-p R2/R5) or CoolProp-compatible (the IF97 library's documented fast default)? This sets the oracle tolerance. | INCOMP baseline: match v8 data, including known-bad fits behind a divergence register, or adopt master's scrubbed data and Chebyshev caloric entries? | Humid air arbiter: RP-1485 (what CoolProp reproduces) or IAPWS G8-10 (whose C_aww constants differ from CoolProp's)? | Ice g00: adopt the R10-06(2009) value by default? RP-1485 may have used the 2006 value. | Bollengier: is it in scope before the oracle includes it, and is its coefficient provenance (paywalled supplement, MIT-shipped) acceptable? | Does the user have a REFPROP licence for local second-oracle runs, and which version?

### 08-tabular-surrogates
- Do not port TTSE/BICUBIC. Four crash or silent-garbage bugs (R1, R2, R3b, R9) were reproduced on the 8.0.0 oracle, and R1, R3b and R7 persist on master. The oracle tests for any future Rust surrogate must include cold-build-then-query, non-square grids, exact-node probes and dome-edge batch probes.
- Grid locate must be a tested partition_point with explicit exact-hit, endpoint and NaN semantics. CoolProp's hand-rolled bisect_vector mis-locates on exact node hits (R3b). Exact node hits are common in sweeps and with round numbers.
- Batch API: the AbstractState fast_evaluate contract (no allocation, no cached-state mutation) is broken by every override, IF97 included. Make the Rust batch API take &self over immutable Arc'd data with caller-owned buffers, enforced by tests, and give it a distinct TwoPhase/OutOfDomain status. Never fall back silently to a neighbour cell.
- Saturation boundaries: build one SA-backed SaturationCurve, but keep a no-SA path. 6 of 136 CoolProp fluid files (Air, R404A, R407C, R410A, R507A, SES36), plus REFPROP/IF97 sources, have no superancillary.
- Cache keys: content-address artifacts (model data hash + builder version + options + format) and store enums by stable string ids. CoolProp's manual kRevision with raw-int enums has already produced a silent-misdecode hazard (post-v8 9b35f538), and the tabular revisions are not tied to content.
- Builds must be explicit and out of the request path. The lazy DT/PS builds cause a ~5 s first-query stall. resolve_point_ is documented as pure yet flashes the exact model and mutates state, so make classify, evaluate and exact-fallback separate passes.
- Critical region: CoolProp's calibration can only shrink from a Water-sized box, and calibrator failures are silent. Prefer POWER-axis NC regions with a recorded build-time validity mask and error budget per (region, property).
- Accuracy gates: CoolProp's SVDSBTL tests gate at 5e-3/1e-3, and its G13-15 fail-map has no assertions. The Rust TDD harness should assert per-property budgets against the exact model, including mid-cell, node and boundary probes, from the start.
- Open questions: Should the Rust surrogate generate superancillaries for the 6 no-SA fluids, or route their dome edges to the exact model? | What accuracy budget should the surrogate tier commit to: G13-15 for water only, or a relative bound against the exact model for all fluids? CoolProp HEOS presets reach ~1-3% near critical (3.0e-2 reproduced at 669 K, 27.5 MPa). | Is two-phase cp/cv/w blending (still present in master tabular) ever acceptable, or must the surrogate return Undefined like the exact model? | Should prebuilt artifacts ship as data crates (needed for WASM, where a ~50 s cold build is unacceptable) instead of a build-time SVD dependency?

### 09-data-assets
- The v8.0.0 data are 89.8 % SA Chebyshev tables, and as raw f64 the whole 136-fluid library is 2.81 MiB (about 22 KiB per fluid). A versioned little-endian binary section format with include_bytes! beats CBOR/JSON at runtime, and compression gains only 13-19 %.
- All SA pieces are degree 12, and p, rho' and rho'' share one breakpoint array in 130/130 fluids. - Datagen must parse with a literal-kind-preserving reader (int vs float), because the FNV-1a source_eos_hash distinguishes 1 from 1.0 and covers strings. All 130 stamps recompute, so the hash can serve as a build-time freshness gate.
- A serde-derived reader rejects v8.0.0 Chlorine.json (duplicate source_eos_hash key), so datagen needs a logged duplicate-key waiver or a pre-clean step.
- Use an immutable Arc<FluidModel> per fluid with lazy OnceLock materialisation and a reference state passed as a value. CoolProp's global mutable library, unsynchronised writers and per-state deep copies (78-126 KiB) are the main obstacles to concurrency and memory scaling.
- One shared case-folded identifier resolver is safe: 556 distinct keys (6.9 KB), no cross-fluid collisions, all ASCII. Lookup behaviour now differs by backend (HEOS lacks upper(name); cubic lacks CAS; PC-SAFT lacks upper(name)), so parity tests should compare successful lookups only.
